# WireDroid — аналоговий розрахунок та SPICE

Оновлено: **3 жовтня 2026 року**. Реалізований код: `app/src/main/assets/wiredroid/electronics.js` та `spice.js`. Перевірки: `tools/wiredroid/electronics-static-sparse.test.cjs`, `spice.test.cjs`.

## Що працює у WireDroid

Вбудований solver розраховує MNA-мережу з простими R/C/L, джерелами, діодами/LED, параметричними транзисторами та наявними моделями моторів. Для понад 96 невідомих використовується розріджена Gaussian elimination з вибором головного елемента. До 96 — щільна матриця. Максимум 1024 невідомих включає вузлові напруги та додаткові струми ідеальних джерел; це не кількість компонентів.

Є два спільні обмеження для всіх Newton-ітерацій одного solve: 30 млн врахованих операцій sparse elimination та 400 тис. ненульових елементів матриці. До 160 Newton-ітерацій; незбіжна або надто щільна мережа завершується явною помилкою. Лічильник операцій включає пошук pivot, оновлення коефіцієнтів і back-substitution; він не є жорстким лімітом часу CPU. `result.method`, `unknowns`, `sparseWork`, `sparsePeakEntries` дають вимірювані показники. Map-матриця зменшує зберігання для розріджених мереж; це не гарантія прискорення проти щільного Float64Array.

Еталонні перевірки порівнюють dense/sparse на незалежних матрицях та ланцюжку 250 резисторів з аналітичними напругами і струмом. Ланцюжок 1000 резисторів має 1001 невідому й близько 3000 ненульових елементів. На поточному комп’ютері один тестовий прогін дав приблизно 52 ms для 250 резисторів sparse, 12 ms dense, 225 ms для 1000 резисторів sparse. Це вимірювання розробки, а не Android benchmark або обіцянка швидкості на планшеті.

`dt=0` означає статичне переобчислення клем при незмінному віртуальному часі: C утримує напругу, L/обмотки — струм, ротори — положення та швидкість. Виходи GPIO можуть змінювати поточні клемні напруги/струми, але pause та події з однаковим timestamp не просувають динамічну пам’ять. Позитивний `dt` інтегрує стан; від’ємний/нечисловий крок відхиляється.

## Експорт netlist

`WireSpice.exportCircuit(scene, catalog, options)` повертає:

```js
{
  netlist,    // текст .cir/.sp, без виконання зовнішньої програми
  pins,       // Object: ключ node:pin -> назва вузла SPICE
  warnings,   // компоненти, виключені тільки при явному ignoreUnsupported
  modelCount
}
```

Підтримані R, C, L, ідеальні батареї, дві ноги потенціометра, діоди/LED, NPN/PNP та NMOS/PMOS LEVEL=1. Мідні з’єднання, внутрішні GND плати й обраний опорний вузол утворюють netlist. Виходи Arduino експортуються як джерела Thévenin з опором профілю плати; pullup/pulldown — як резистори. Поточний PWM експортується як середня напруга; це статичний знімок GPIO, без часової форми MCU.

Параметри `options`:

- `outputs`, `modes`, `inputs` — Map поточного стану GPIO/потенціометрів; `pressed` — Set натиснутих перемикачів.
- `reference: {node, pin}` — явний опорний контакт. За відсутності вибирається GND першої плати або мінус першої батареї. Відсутність/помилка опори відхиляється.
- `initial: Map(nodeId -> {voltage, current})` — початкові умови C/L. За відсутності — нуль.
- `transient: {step, stop}` — `.tran ... uic`; максимум 1 млн заданих інтервалів. Без параметра генерується `.op`.
- `models` — текст дозволених числових `.model`, описаний нижче.
- `ignoreUnsupported: true` — явне виключення непідтриманих деталей з повідомленнями. За замовчуванням експорт з такими деталями відхиляється.

Кнопки/мікросхеми, MCU, серво, ESC, драйвери та мотори не стають автоматично повними SPICE-моделями. Дозволений експорт стосується аналогових примітивів. Імена елементів/вузлів генерує WireDroid, користувацькі назви залишаються лише очищеними коментарями. Ідентичні паралельні джерела дедуплікуються; джерела різної напруги на одній парі вузлів відхиляються.

У `spice.test.cjs` перевірені синтаксис deck, відповідність контактів, RC/початкові умови, PWM знімок, підтягування, числові моделі, відхилення невідомих деталей/небезпечних директив і дільник 2.5 V. **Зовнішній ngspice у цьому етапі не встановлено й не запущено; зовнішня верифікація числових SPICE-результатів ще потрібна.**

## Користувацькі числові моделі

`WireSpice.parseModels(text)` приймає максимум 128 KiB та 128 моделей `.model NAME D/NPN/PNP/NMOS/PMOS(...)`. Ім’я починається з літери, має до 32 символів літери/цифри/underscore; `WD_DEFAULT_...` зарезервовано. Дозволені лише перелічені в `spice.js` числові параметри; для MOS — LEVEL=1. Підтримані коментарі `*` та продовження `+`.

```spice
.model MY_DIODE D(IS=2n N=1.8 RS=0.5)
.model MY_NMOS NMOS(LEVEL=1 VTO=2.5 KP=0.02)
```

`node.electrical.spiceModel: "MY_DIODE"` вибирає модель для сумісного типу деталі. Модель не міняє вбудований JavaScript solver — використовується лише в експорті. Числа повинні бути скінченними, з модулем не більше 1e18. Відомі суфікси SPICE підтримані; `M` означає milli, `MEG` — mega. Фізична достовірність параметрів потребує окремого джерела виробника.

`.include`, `.control`, `.subckt`, `.param`, вирази, файли, shell-команди, динамічні code models та encrypted vendor models не імпортуються. Такий обмежений формат можна зберігати й експортувати без виконання вмісту імпорту. При використанні чужої моделі потрібно зберегти її походження та дозвіл на розповсюдження; поточний реліз не додає пакета сторонніх моделей.

## Конкретний шлях до ngspice backend

Це наступна інтеграція, яка **ще не реалізована**. Офіційний ngspice підтримує керування через shared library, передачу netlist, окремий потік розрахунку, callbacks з даними, зупинку та продовження. Це дає відповідний механізм для backend, який не блокує редактор. [Офіційний опис shared ngspice](https://ngspice.sourceforge.io/shared.html).

Для Android пропонується ізольований сервіс з JNI-обгорткою та закріпленим source revision, SHA-256 і конфігурацією складання для arm64-v8a/armeabi-v7a/x86_64. `ngSpice_Circ` завантажує згенеровані рядки; `ngSpice_Init_Sync`/GetSyncData та зовнішні voltage/current callbacks потрібні для синхронізації з MCU. `.tran` не можна просто просувати за wall-clock: MCU-події задають найближчу межу віртуального часу, а solver не має її перескакувати. API й transient synchronization описані у [посібнику ngspice](https://ngspice.sourceforge.io/docs/ngspice-manual.pdf). Поточний онлайн-посібник позначено 47+ development, тому перед реалізацією потрібно закріпити посібник тієї самої ревізії, що й бібліотека.

Реалізація має зберігати окрему чергу команд і захищений lifecycle: init → load → run/pause → stop → destroy. Callback копіює лише потрібні вектори, передає пакети на UI й не викликає WebView з native thread. Команда Stop спочатку просить solver зупинитися; watchdog сервісу може завершити завислий native процес. Backend повинен оголошувати підтриманий набір моделей, не підміняти помилку silent fallback і повертати назву деталі/вузла для незбіжної схеми.

Початкові ліміти для майбутнього backend потрібно виміряти на цільовому планшеті: ≤1024 невідомих, ≤128 KiB deck моделей, обмежена кількість записуваних векторів/точок, максимум 10 s wall-clock для batch та можливість cancel. Вони не є характеристиками ngspice та ще не enforced native runtime. Перед включенням потрібні differential tests RC/RL/діода/BJT/MOS проти batch ngspice, same-time MCU events, ADC threshold, PWM edge, pause/resume, cancel, ABI smoke tests, пам’ять і час на реальному Android. Фазовий BLDC, термічний solver та виробничі моделі всіх деталей залишаються окремими завданнями.
